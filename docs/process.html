Beacon CRM → AI-readable architecture

What we're building, and the sequence to get there. Works against any Beacon account.

The goal is to describe the shape of the CRM, not its contents. An AI agent should be able to answer "what can a Grant record hold, what does it link to, what values may that field take, can files attach to it" without ever having seen a real person, organisation, grant or case note.

No records ship. orgs/<org>/out/ contains entity types, fields, field types, select vocabularies, the reference graph, smart-field formulas, rollup configs and which types accept attachments. No record values, no counts, nothing that goes stale as records are added.

Analytics live separately. Record counts and option usage are a snapshot, not architecture, so they go to orgs/<org>/reports/ — regenerated on demand, gitignored, never mixed into the export.

Pipeline

1

Fetch the schema

read-only

One authenticated GET /entity_types. This is configuration, not personal data, so it is taken whole and kept.

  • BEACON_API_KEY from orgs/<org>/.env.local (gitignored)
  • orgs/<org>/beacon-schema-raw.json — no personal data, kept as the source of truth (gitignored along with the rest of orgs/<org>/)
↓
2

Build the schema documents

no network

Pure transformation of step 1. Every reference field names its target entity type IDs, which resolve inside the same response, so the relationship graph falls out of the schema with no extra calls.

  • orgs/<org>/beacon-schema-raw.json
  • orgs/<org>/out/schema.json — every entity type and field, full metadata
  • orgs/<org>/out/relationships.json — reference graph with resolved names and cardinality
  • orgs/<org>/out/attachments.json — which entity types have file fields, and which
↓
3

Usage report (optional, on demand)

optional · separate output

Streams GET /entities/{key} and counts. Answers the practical question: for each select field, how many records hold each option, and which options are used by nobody. That surfaces both data-collection gaps and options worth trimming. Values are counted and discarded; nothing is written to orgs/<org>/out/.

  • live API, ~60 paged GETs, well inside the 300/min limit
  • orgs/<org>/reports/usage.json — per field: fill rate, and per select option, the record count
  • orgs/<org>/reports/usage-summary.md — the digest: unused options, and fields no record has ever filled
↓

Gate — verify_out.py, fails closed

  • Special-category fields (ethnicity, religion, sexual orientation, disability, health, allergies, DOB, gender, right to reside, marital status, net worth) contribute counts only — never observed values, even where the schema keeps the option list.
  • Free-text fields (casework notes, case notes, safeguarding, comments, beneficiary and volunteer notes) contribute fill rate only — never a distinct-value sample.
  • File fields contribute the fact that files may attach — never a filename, never a count of real attachments.
  • No output file may contain an email, phone number, postcode or prose-length string, and no field may go missing. Non-zero exit blocks the commit.
↓
4

Publish

verify_out.py is the gate and it fails closed: it scans for emails, phone numbers, postcodes and prose, rejects any JSON key that would indicate record data, and asserts every field survived the transform. orgs/<org>/out/ stays gitignored regardless — this gate matters if you ever choose to publish one org's export separately from this repo.

  • orgs/<org>/out/
  • the AI-ready dataset for that organisation

What ships, and what doesn't

ThingIn the export?Why
Entity types, fields, labels, keysYes, wholeConfiguration. Not personal data. The core of what the AI needs.
Field types and settingsYes, wholeDecimal places, allow-multiple, read-only, required — all architecture.
Select optionsYes, wholeThe vocabulary is design, not data. Kept even for special-category fields.
Reference graphYes, wholeHow the model hangs together. Derived from the schema alone.
Smart-field formulas, rollup configsYes, wholeBusiness logic. Formula shipped, computed value never.
Layouts and list columnsYesShows what staff actually see and prioritise.
Record counts per typeNot in orgs/<org>/out/Analytics, not architecture. Goes stale. Lives in orgs/<org>/reports/.
Field fill rates, option usageNot in orgs/<org>/out/The point of the separate report: shows unused options worth trimming.
Which types accept attachmentsYesStructural fact about the model.
Any record valuesNoNot needed for architecture. Excluded wholesale rather than sanitised.
Filenames of attachmentsNoFilenames leak names and case detail. Only the capability matters.
Free-text note bodiesNoRedacted as policy, regardless of whether current content is dummy data.
Users, by nameNoCount and role distribution only.

Status and open points

  1. Read-only, absolutely. beacon.py hardcodes method="GET" and its self-check fails if the strings POST, PATCH, PUT or DELETE ever appear in the client. There is no write path in this project.
  2. Unused select options turn up in most accounts — orgs/<org>/reports/usage-summary.md lists them by entity type. Worth a pass to decide which are gaps in data collection and which are options to retire.
  3. orgs/<org>/ stays entirely gitignored, inputs and generated output alike. This repo carries no organisation's credentials, branding, schema or record counts — only the generic tooling.
